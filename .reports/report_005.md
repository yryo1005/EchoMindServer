# EchoMindServer ブラウザフロントエンド実装レポート

## 1. 目的

iPhoneアプリ(常時録音・アップロード，本タスク対象外)とは別に，ブラウザから質問(QA)および過去の会話の閲覧・音声再生を行うためのフロントエンドを，`programs/server/`に追加実装した．

## 2. 実装内容

### 2.1 技術構成

ビルドツール(npm等)を導入しない，プレーンなHTML/JavaScript/CSSで実装した(`programs/server/static/`)．FastAPIの`StaticFiles`によりAPIと同一ホスト・ポートから配信するため，CORS設定は不要である．

### 2.2 追加したバックエンドAPI

既存の`POST /api/upload`，`POST /api/chat`に加え，フロントエンドの「過去の会話を聞く」機能のために以下を追加した．

- `GET /api/persons`: 登録されている人物の一覧(発話数の多い順)．
- `GET /api/conversations`: 会話の一覧(開始時刻の新しい順，`limit`/`offset`/`person_id`で絞り込み可能)．
- `GET /api/conversations/{conversation_id}`: 指定した会話の発言一覧(発言ごとに音声URLを含む)．
- `GET /api/audio/{utterance_id}`: 発言の音声クリップ(wav)を配信する．

### 2.3 フロントエンド

`index.html`にタブ切り替えのUIを実装し，2つの機能を提供する．

- **質問する**: テキストボックスに質問を入力すると`POST /api/chat`を呼び出し，回答と参照タイムスタンプを表示する．
- **過去の会話を聞く**: 会話一覧(参加者名・発言数)をサイドバーに表示し，選択すると発言一覧(発言者，タイムスタンプ，テキスト，`<audio>`要素による再生コントロール)を表示する．

`app.js`では，ASR・LLMが生成したテキストをHTMLに挿入する際に`escapeHtml`関数でエスケープし，XSSを防止している．

## 3. 動作確認

既存の動作確認用データ(`conv_000.wav`由来の34発言，3話者)を用いて以下を確認した．

- `GET /`でフロントエンド(`index.html`，`app.js`，`style.css`)が正しく配信される．
- `GET /api/conversations`，`GET /api/persons`，`GET /api/conversations/{id}`が期待する形式のJSONを返す．
- `GET /api/audio/{utterance_id}`が有効なwavファイル(16kHzモノラル)を返す．
- `POST /api/chat`がブラウザからの呼び出し形式(`user_id`，`query`)で正しく応答する．

## 4. 追記: favicon・会話の分割・人物名の手動設定への対応

動作確認の過程でユーザーから寄せられた以下の点に対応した．

### 4.1 `/favicon.ico`の404ログ

ブラウザが自動的に要求する`/favicon.ico`に対し，`app/main.py`に`204 No Content`を返す専用エンドポイントを追加した．動作上の不具合ではなく，ログに404が記録されるだけの事象だった．

### 4.2 会話一覧が発言単位で分割される件

`programs/server/app/pipeline/orchestrator.py`の設計は「1回のアップロード(音声ファイル)= 1つの会話(Conversation)」であり，その中で検出された全ての発話区間が1つの会話にまとめて紐づく．動作確認用データとして`ex002_model_benchmark`/`ex003_server_evaluation`の疑似「セッション」(各ファイルが2〜3発話程度の短い会話)を1件ずつ個別にアップロードした場合，各ファイルがそれぞれ別の短い会話として登録されるのは意図した挙動である．実際の運用(iPhoneから1時間ごとの録音ファイルをアップロード)では，1回のアップロードに含まれる会話がまとめて1つの会話として記録される．

### 4.3 人物IDの統合・名前の手動設定

話者IDの人物IDへの統合自体は既に実装・検証済み(`.reports/report_004.md`，純度92.5%)であり，同一人物には既に一意の人物IDが割り当てられている．名前が全員「不明」(`null`)であったのは，動作確認用データ(JVSコーパスの朗読文)に自己紹介等の名前を特定できる発言内容が含まれていなかったためである．

これに対し，ブラウザから人物IDに名前を手動で設定できる機能を追加した．

- バックエンド: `PUT /api/persons/{person_id}/name`を`app/api/browse.py`に追加した．
- フロントエンド: 「話者の名前を設定」タブを追加し，人物一覧(人物ID，名前の入力欄，発話数)を表形式で表示し，名前を入力して保存すると即座にDBへ反映される．

動作確認: 人物の名前を手動で設定し，`GET /api/persons`および`GET /api/conversations`の両方に設定した名前が反映されることを確認した．

## 5. 追記: アカウント登録・ログイン機能の追加

前節で挙げた「認証・アクセス制御が実装されていない」という論点に対応し，メールアドレス+パスワードによるアカウント登録・ログイン機能を実装した．

### 5.1 データベース設計の変更

`User`テーブル(`user_id`, `email`, `password_hash`, `role`)を追加した．`Person`・`Conversation`それぞれに`user_id`外部キーを追加し，アカウントごとにデータを分離する構造に変更した(`Utterance`は`Conversation`経由で間接的にアカウントに属する)．パスワードはbcryptでハッシュ化して保存する．

### 5.2 認証方式

JWT(Bearer Token，HS256，有効期限7日間)による認証を実装した(`app/auth.py`)．署名鍵は`tokens.json`の`jwt_secret`に自動生成・保存される．

- `POST /api/auth/register`: アカウント登録(メールアドレス+パスワード，8文字以上)．登録直後にアクセストークンを発行する．
- `POST /api/auth/login`: ログイン．
- `GET /api/auth/me`: 現在ログイン中のユーザー情報を取得する．

既存の`POST /api/upload`，`POST /api/chat`，`GET /api/persons`，`PUT /api/persons/{id}/name`，`GET /api/conversations`，`GET /api/conversations/{id}`，`GET /api/audio/{id}`の全てに認証(`Depends(get_current_user)`)を必須にし，自分のアカウントのデータのみを対象とするよう変更した．話者ID統合(`resolve_person`)も，同一アカウント内の人物のみを照合対象とするよう変更した(他アカウントの人物と誤って統合されることを防ぐ)．

### 5.3 既存データ(デバッグ用データ)の移行

アカウント機能の追加前に作成された`Person`・`Conversation`にはuser_id列が存在しなかったため，一度限りの移行スクリプト`programs/server/scripts/assign_existing_data_to_user.py`を作成した．このスクリプトは

1. `persons`・`conversations`テーブルに`user_id`列を追加する(`ALTER TABLE ... ADD COLUMN IF NOT EXISTS`)．
2. 指定したメールアドレス(事前にブラウザのアカウント登録フォームで登録しておく)のアカウントへ，`user_id`が未設定の既存データを帰属づける．
3. そのアカウントのロールを`admin`に変更する．

という処理を行う．AIエディタがパスワードを直接扱わないよう，スクリプトはメールアドレスのみを受け取り，パスワードは事前にユーザー自身がブラウザから登録する設計とした．

### 5.4 フロントエンドの変更

`index.html`にログイン・アカウント登録フォーム(`auth-screen`)を追加し，未ログイン時はこの画面のみを表示する．ログイン後，アクセストークンをブラウザの`localStorage`に保存し，以降のAPI呼び出しに`Authorization: Bearer`ヘッダとして付与する(`authorizedFetch`関数)．401が返った場合は自動的にログイン画面に戻る．ヘッダにログイン中のメールアドレス表示とログアウトボタンを追加した．音声再生(`<audio>`要素)も認証が必要なため，`authorizedFetch`でBlobとして取得し，Object URLを生成して再生する方式に変更した．

### 5.5 動作確認

- 新規アカウントを登録し，ログインでアクセストークンが発行されることを確認した．
- 認証なしで各API(`/api/upload`, `/api/chat`, `/api/conversations`, `/api/audio/{id}`)を呼び出すと401が返ることを確認した．
- 移行スクリプトを実行し，既存のデバッグ用データ(3人物，1会話)が指定したアカウントに帰属づけられ，そのアカウントのロールが`admin`になることを確認した．
- 別の新規アカウントでログインした場合，既存データが一切見えない(データ分離が機能している)ことを確認した．
- 認証済みで新たに音声をアップロードし，新しい会話が正しく自分のアカウントに紐づくことを確認した．

## 6. 未解決の論点・次に検討すべき事項

- パスワードリセット・メールアドレス確認(verification)・リフレッシュトークンは未実装．
- JWTの失効(ログアウト時の即時無効化，漏洩時の強制失効)は未対応．現状はクライアント側でトークンを破棄するのみで，サーバー側では有効期限(7日間)まで有効である．
- iPhoneアプリ(本タスク対象外)は，ログイン画面の実装と，取得したアクセストークンを`Authorization`ヘッダに付与して`/api/upload`・`/api/chat`・`/api/conversations`等を呼び出す実装が必要である．
- 会話一覧はページネーション(`limit`/`offset`)のAPIのみ用意し，フロントエンド側のページ送りUIは未実装(現状は50件まで一括表示)．
- フロントエンドの自動テスト(E2Eテスト等)は未実装．
- 長時間の録音(1時間チャンク)の中に時間的に離れた複数の会話が含まれる場合，現状は全体を1つの会話として扱う．無音区間の長さ等に基づき，1回のアップロード内で複数の会話に分割するロジックは未実装であり，今後の検討課題である．
