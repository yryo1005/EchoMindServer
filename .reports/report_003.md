# EchoMindServer サーバー実装レポート(programs/server/)

## 1. 目的

`.reports/report_001.md`, `.reports/report_002.md`のベンチマーク結果に基づき，仕様書記載のモデル(Haas-ja-v1.0, pyannote/speaker-diarization-3.1, ruri-large-v2, Gemini API)が妥当であると判断し，EchoMindサーバー本体(`programs/server/`)を実装した．

## 2. 実装内容

### 2.1 構成

- **Webフレームワーク**: FastAPI
- **データベース**: PostgreSQL + pgvector(docker-composeで起動)
- **モデル構成**(各ベンチマークの結果に基づく最終選定):
  - VAD: Silero VAD
  - 話者分離: `pyannote/speaker-diarization-3.1`(256次元の話者埋め込みも同時取得)
  - 音声認識: `Haas-ja-v1.0`
  - 文章ベクトル化: `cl-nagoya/ruri-large-v2`(1024次元)
  - 回答生成: Gemini API(`gemini-3.1-flash-lite`)

### 2.2 データベース設計

仕様書「4. データベース設計の要点」に基づき，以下の3テーブルで「会話」-「発言」の階層構造を実装した．

- `persons`: DB全体で一意な人物．256次元の代表話者埋め込み(`representative_embedding`)と発話数(`utterance_count`)を保持する．
- `conversations`: 会話単位．開始・終了時刻と元音声ファイルのパスを保持する．
- `utterances`: 発言単位．会話・人物への外部キー，タイムスタンプ，テキスト，音声パス，1024次元の文章埋め込み，256次元の話者埋め込みを保持する．

### 2.3 常時処理パイプライン(`POST /api/upload`)

仕様書「3.2」のSTEP1〜5に対応し，以下をバックグラウンドタスクとして実行する．

1. Silero VADで発話区間を抽出(全体が無音の場合は何もしない)．
2. pyannote 3.1で話者分離を行い，話者が2名未満の場合は「会話」として扱わず処理を終了する．
3. 話者区間ごとに音声を切り出す．
4. Haas-jaで文字起こしし，Gemini APIで文章校正，ruri-large-v2でベクトル化する．
5. 話者埋め込みの類似度(閾値0.7)に基づき既存の人物IDへ統合，または新規人物を作成し，DBへ保存する．発話数が10件を超えた人物については，Gemini APIで会話文脈から名前推定を試みる．

### 2.4 QAフロー(`POST /api/chat`)

仕様書「3.3」に対応し，以下を実行する．

1. 質問文をruri-large-v2でベクトル化する．
2. pgvectorのコサイン距離により類似度上位5件の発言を検索する．
3. 検索された各発言について，同一会話内の前後2発言を加えて会話コンテキストを補う．
4. コンテキストと質問文をGemini APIへ送信し，回答を生成する．
5. 回答テキストと，検索された発言の参照タイムスタンプを返却する．

## 3. 動作確認

ex002_model_benchmarkの疑似会話データ(`conv_000.wav`，3話者，約80秒)を用いてE2Eで動作確認を行った．

- `POST /api/upload`: 202相当の受付レスポンスを確認後，バックグラウンド処理で34件の発言がDBに保存され，3名の人物(Person)が正しく識別された．
- `POST /api/chat`: 「ランチに関する話はありましたか？」という質問に対し，該当する発言(「日時を決めて，一緒にランチを食べよう。」)を正しく検索し，その内容に基づいた回答と参照タイムスタンプが返却された．
- Gemini API無料枠のレート制限(1分あたり15リクエスト)に対しては，`tenacity`による指数バックオフ付きリトライを`app/services/gemini_client.py`に実装し，エラーなく処理が完了することを確認した．

テスト: `tests/test_server.py`で，話者ID統合に用いるコサイン類似度計算のユニットテストを実装し，全て合格することを確認した(モデルロードやDB接続を伴う結合テストは未実装)．

## 4. 未解決の論点・次に検討すべき事項

- 話者ID統合のアルゴリズム(閾値0.7での最近傍探索)は未チューニングであり，実際の長期運用でどの程度の精度が出るかは未検証．特に，似た声質の人物の誤統合や，同一人物が別人物として分裂するケースの検証が必要．
- 名前推定(`maybe_estimate_name`)は，会話内の呼びかけや自己紹介に依存するヒューリスティックであり，精度は未評価．実際の会話データでの検証が必要．
- iPhoneアプリ側(常時録音・Wi-Fi/充電時アップロード)は本タスクの対象外であり，未実装．
- Cloudflare Tunnelsによる公開は，サーバー運用環境(自宅PC)側での設定が必要であり，本タスクでは未対応．
- DBマイグレーション(Alembic等)は未導入で，現状`Base.metadata.create_all()`によるテーブル作成のみ行っている．スキーマ変更が発生した場合の移行手順を別途整備する必要がある．
- 結合テスト(実際のモデル・DBを用いたE2Eテスト)はpytestに組み込まれておらず，手動のcurl確認のみで動作を確認した．CI等での自動テスト化が今後の課題である．
