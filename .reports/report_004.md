# EchoMindServer 精度検証レポート(ex003_server_evaluation)

## 1. 目的

`.reports/report_003.md`の「未解決の論点」で挙げた，サーバーパイプライン(`programs/server/`)における話者ID統合(話者埋め込みの類似度に基づく人物ID統合)と名前推定(Gemini APIによる会話文脈からの名前推定)の精度を検証した．評価は`programs/ex003_server_evaluation/`で実施した．

## 2. 話者ID統合の精度検証

### 2.1 検証方法

JVSコーパスの話者プール(10名)から，同一話者が複数の別々の「会話」(アップロード)に跨って登場する疑似データを15件生成した(`data_speaker_id.py`)．各セッションは2〜3名の話者から3〜5発話で構成され，ex002と同様に重複発話・加算的ノイズ(SNR 10〜25dB)を含む，実運用に近い条件とした．

これを実際のサーバーパイプライン(`app/pipeline/orchestrator.py`)に，本番用DBとは別の評価用DB(`echomind_eval`)を用いて順次通した．各セッションは「十分な時間差を空けた別々のアップロード」としてシミュレートしている．話者ID統合の精度のみを対象とするため，Gemini APIを用いる文章校正・名前推定は無効化した(無料枠のクォータ節約のため)．

評価指標として，予測された人物ID(Person)ごとの正解話者(JVSラベル)の一致率の平均("person_purity")と，その逆(正解話者ごとの多数派人物IDへの集約率の平均，"speaker_recall")を計算した．発話境界は話者分離の結果，正解データの境界と完全には一致しないため，時間的重なりが最大の正解区間の話者を対応する正解ラベルとした．

### 2.2 結果

| 指標 | 値 |
| :--- | :--- |
| person_purity | 0.925 |
| speaker_recall | 0.925 |
| 正解話者数 | 10 |
| 予測された人物数 | 10 |

正解話者数(10名)と予測された人物数(10名)が完全に一致し，話者ID統合の閾値(`SPEAKER_MATCH_THRESHOLD=0.7`)は，本検証データにおいて話者の過剰統合(異なる人物を同一人物とみなす)・過剰分裂(同一人物を複数の人物とみなす)のいずれも起こしていないことが確認できた．純度92.5%は，話者分離自体の誤り(オーバーラップ発話の誤帰属等)に起因するものと考えられ，話者埋め込みによる統合ロジック自体は妥当に機能している．

## 3. 名前推定の精度検証

### 3.1 検証方法

音声合成(TTS)が利用できないため，この検証はASRより後段のロジック(会話テキストからGemini APIで名前を推定する処理，`app/pipeline/person_identification.estimate_name_from_context`)に限定した．Gemini APIを用いて，自己紹介や呼びかけ等により対象人物の名前が特定できる疑似会話テキストを20件生成した(`data_name_estimation.py`)．名前が直接的に明示される"easy"(10件)と，間接的な手がかりのみで推測が必要な"hard"(10件)の2種類の難易度を設定した．

生成したテストケースに対し，サーバーが実際に使用している名前推定関数を適用し，推定された名前が正解と一致するか(敬称等の表記ゆれは部分一致で許容)を評価した．

### 3.2 結果

| 条件 | 正解率 |
| :--- | :--- |
| 全体 | 0.75 |
| easy | 0.90 |
| hard | 0.60 |

名前が明示的に述べられる"easy"条件では高い精度(90%)が得られた一方，間接的な手がかりのみの"hard"条件では精度が低下した(60%)．誤り(5件)は全て「不明」と出力するものであり，誤った名前を確信的に出力する(偽陽性)誤りは観測されなかった．これは，誤った情報をユーザーに提示するリスクが低い，安全側に倒れた挙動であり，実運用上望ましい特性である．

なお，生成されたテストケースの対象人物名は，同一の名前("佐藤"，"健太"，"健二")が繰り返し出現しており，Gemini APIによるテストケース生成自体の多様性には限界があった．この点は本検証結果の一般化可能性を制限する要因であり，より多様な名前・会話パターンでの追加検証が望ましい．

## 4. 全体の考察

- 話者ID統合は，実運用に近い(重複発話・ノイズを含む)条件下でも高い精度(純度92.5%)を示し，閾値0.7は妥当な設定であることが確認された．
- 名前推定は，名前が明示される場合には高精度(90%)だが，間接的な手がかりのみの場合は精度が下がる(60%)．ただし誤りは「不明」への倒れ込みであり，誤情報を提示するリスクは低い．
- 両検証とも，Gemini API無料枠の1日あたりのリクエスト数上限(500件/モデル)に複数回到達し，検証の実施自体に制約が生じた．本番運用においても，大量の発話を処理する際にはこの制約が問題になり得るため，有料枠への移行やモデルの分散利用を検討する必要がある．

## 5. 未解決の論点・次に検討すべき事項

- 本検証の疑似データは，JVSコーパス(クリーンな朗読音声)を基にしたものであり，実際の自然な会話(感情表現，方言，長期間の声質変化等)における話者ID統合の精度は未検証である．
- 名前推定のテストケースは，Gemini自身が生成したものであり，名前のバリエーションが少なく，生成モデルと評価モデルが同一(Gemini)であることによる楽観的な評価になっている可能性がある．人手で作成したテストケースでの追加検証が望ましい．
- 話者ID統合の閾値(0.7)は，本検証データに対しては妥当であったが，話者数が増える(数百人規模)運用では，閾値の再チューニングやクラスタリング手法の見直しが必要になる可能性がある．
- Gemini API無料枠のレート制限・日次上限は，本番運用における実際のボトルネックとなり得るため，運用開始前に有料枠への移行を検討する必要がある．
