# Order 009

## ユーザーからの指示（原文）

今のプログラムではサーバーの受け取り時間をタイムスタンプとしていますが，それだとクライアントが送ったタイミングの録音と誤認してしまいます．クライアント側からいつの録音であるかをアップロードする前提に変更してください
例えばクライアントから送られるファイル名が録音開始時間から終了時間になっていると楽でしょうか
方法は委ねます

現在のサーバーは拡張子に関係なく .wav で保存し、librosa で16kHzモノラルとして読み込みます。
クライアントからAACで送る想定とし，RAW音源である必要はないので，軽量なフォーマットでサーバーでは保存するようにしてください

アップロードの応答だけが失われたとき、クライアントが再送すると同じ音声が二重に処理されます。クライアントでファイルIDを付け、サーバーで重複を弾く対策を推奨します。
処理済み音声のSHA256を覚えておく等の工夫が必要ですかね？方法は任意に委ねます．

サーバーの公開はCloudFlareですでに所有しているドメインのDNSで実施します
これを前提にセットアップと，私がCloudflareでどの操作をしないといけない窯で出力してください
DNS records for stargazyguys.com

## 指示の解釈

4点の改善を実施する．方法の詳細はAIエディタに委ねられている．

1. **録音タイムスタンプ**: サーバー受信時刻ではなく，クライアントが報告する録音開始時刻を発言タイムスタンプの基準とする．ファイル名エンコード方式も提案されたが，実装・解析の複雑さを避けるため，`POST /api/upload`の明示的なフォームフィールド(`recorded_started_at`，ISO8601)として送る方式を採用する．

2. **軽量な音声形式**: クライアントがAACで送信する前提のもと，サーバーも非圧縮wavでの保存をやめ，アップロードされたファイルは元の拡張子のまま保存し，サーバー側で切り出す発話クリップもAAC(.m4a)で保存する．

3. **重複アップロード防止**: アップロードされた音声データのSHA256ハッシュを用いた冪等性チェックを実装する(`UploadRecord`テーブル)．同一アカウント内で同じハッシュのアップロードがあれば再処理せず，過去の処理結果を返す．クライアント発行のファイルID(`client_file_id`)も補助的に記録する．

4. **Cloudflare Tunnelでの公開**: 既存ドメイン`stargazyguys.com`(Cloudflareで管理)を前提に，`docker-compose.yml`へ`cloudflared`サービスを追加する．AIエディタはユーザーのCloudflareアカウントを操作できないため，ユーザーがCloudflareダッシュボードで実施すべき操作(トンネルの作成，Public Hostnameの追加によるDNSレコードの自動作成等)を`.reports/report_006.md`に具体的な手順として記載する．

いずれもAIエディタの判断で方法を決定したため，`.reports/report_006.md`に設計上の理由・動作確認結果をまとめた．
